# PocketHost Alpha repository audit — 2026-11-28

## Scope and method
Reviewed the complete Alpha repository tree (379 entries at the time of this audit), Android Gradle project structure, app and runtime-worker manifests/build configuration, launcher resource generation, DDNS implementation and UI, hosting service paths, workflow definitions, and existing validation scripts/tests. This is a static repository audit; it is not a physical-device, carrier-network, DNS propagation, or production-gateway acceptance test.

## Confirmed defects fixed in this change
1. **Android resource merge blocker:** the checked-in `app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml` duplicated the same resource generated by `GeneratePocketHostLauncherIcons`. The checked-in duplicate is removed; generated branding resources are the sole owner of that resource.
2. **Workflow responsibility overlap:** the previous workflows mixed app APK creation, runtime-worker APK creation, emulator testing, Android quality, native compilation, Python, Rust, control-plane and web-console checks. These workflows are replaced with independently scoped workflows:
   - `android-app-build.yml`
   - `runtime-worker-build.yml`
   - `android-app-quality.yml`
   - `runtime-worker-quality.yml`
   - `rust-hosting-engine.yml`
   - `native-relay-node.yml`
   - `control-plane.yml`
   - `deployment-infrastructure.yml`
   - `web-console.yml`
   - `linux-agent.yml`
   - `runtime-python.yml`
   - `node-runtime.yml`
   - `protocol-contracts.yml`
   - `trusted-proxy-security.yml`
   - `android-integration-acceptance.yml` is a separate cross-module acceptance workflow; it installs two distinct APKs rather than merging them.
3. **APK boundary:** app and runtime-worker build jobs are separate. App build asserts that the runtime-worker APK is not embedded. Runtime-worker build verifies its own package ID and Node native libraries.

## Architecture verified from source
- Gradle includes `:app` and `:runtime-worker` as distinct Android application modules with distinct application IDs.
- The runtime worker declares a signature-protected binding permission; the host app requests it.
- The app has separate hosting, relay, DNS, runtime-client, storage, diagnostics and management packages.
- Rust hosting engine and relay node are independent Cargo projects.
- Control plane, Caddy deployment, web console, Linux agent, protocol schemas and runtime catalog are separate repository areas.
- Dynadot and Cloudflare DDNS provider selection is explicit. Dynadot credentials are stored encrypted with Android Keystore; Cloudflare token handling remains separate.
- DDNS independently detects IPv4/IPv6 and refuses non-global addresses; public address detection is not represented as proof of inbound reachability.

## Remaining risks / acceptance work
These are not honestly certifiable from repository source alone:
- Build and test workflows must complete on the new commit; a committed workflow is not a passing workflow.
- Run instrumentation on an emulator and on the actual Vivo Y95. Vendor battery management, Android foreground-service policy, process reclaim and thermal/memory limits require device tests.
- Test inbound IPv4 and IPv6 from an external network. A globally routable address does not prove firewall/router/carrier reachability. CGNAT may require a public relay.
- Validate Dynadot DDNS against the live account/domain without exposing the DDNS password. DNS propagation and resolver caches are external.
- Verify end-to-end HTTPS, certificate issuance/renewal, hostname routing, relay reconnect/recovery and visitor traffic through a real public gateway.
- Review every third-party runtime binary/license and pin/update policy as part of release engineering.
- The app's Android instrumentation suite and worker service lifecycle need a dedicated integration acceptance run after independent module builds are green.

## Workflow policy
Each workflow owns one product area and produces its own result. App and Runtime Worker APKs are built and uploaded independently. Cross-process integration tests may install both separately-built APKs, but must never bundle one APK inside the other.


## Matched APK signing requirement
The host and runtime worker use a signature-protected Binder permission. APKs built in separate fresh GitHub-hosted jobs may have different debug signing certificates and must not be treated as an installable pair. Use the matched two-file artifact emitted by the Android Integration Acceptance workflow, which builds both modules on one runner with the same debug key. The integration workflow builds all supported ABIs. Production release signing must use the same protected keystore for both APKs; see `docs/APK_SIGNING_AND_INSTALLATION.md`.

## Additional DDNS hardening
Dynadot response handling now requires a JSON response containing `error_code`; only codes other than `-1` count as accepted. HTML, login/challenge pages, missing codes and explicit API failures are rejected. Instrumentation coverage exercises success, error, malformed HTML and missing-code responses.


## Further findings and fixes from the full-source pass
- Replaced the legacy instrumentation assertion that expected an embedded worker APK. The test now asserts the worker is separately installed and absent from the host APK.
- Tightened Dynadot response handling to require its JSON `error_code` contract, with instrumentation tests for success, explicit failure, malformed HTML and missing code.
- Expanded dual-stack public-address filtering to reject additional IANA special-purpose IPv4/IPv6 ranges and added regression cases.
- Runtime status/stop paths no longer report `STOPPED` merely because a Binder connection is absent. Background status/stop calls bind and query the installed companion; UI refresh performs those calls off the main thread. Resource-limit changes now fail closed if status/stop cannot be verified.
- The app and worker APK workflows now verify their own packaged native libraries for all three supported ABIs. The lock refresh workflow covers both Android modules.
- UI review found product gaps that are explicitly surfaced rather than hidden: live Deployments/rollback and in-app Cloudflare Access policy management are not implemented.
- Runtime security boundary limitations are documented in `docs/RUNTIME_SECURITY_MODEL.md`. Current Python/Node customer code runs under the shared companion UID; the isolated-process/seccomp probe is not production per-project isolation.

- Removed the remaining checked-in legacy launcher XML/drawable/color resources so pre-26 density PNGs and the generated v26 adaptive icon are the only launcher resources. This avoids an anydpi XML overriding the generated 48dp legacy icons.
- Pinned the cloudflared Android source build to immutable upstream commit `b0297f0b24c60a4cef743b7b878e2da3798cb839` instead of trusting a mutable release tag alone.
- Split native engine, native relay, Linux agent and protocol-contract checks into independent workflows; split deployment infrastructure validation from the web-console build.

- Split Python WSGI runtime, Node preload smoke tests, Linux agent tests, protocol contract tests and trusted-proxy spoofing tests into their own workflow files; each now has independent triggers and concurrency.

## CI issue discovered during verification
The first Android app quality run exposed a YAML flow-mapping error: the unquoted comma-separated Rust target list was parsed as multiple mapping keys, so only `aarch64-linux-android` was installed. The workflow now passes the complete list as a block scalar. The corrected Android app quality rerun is in progress; the initial failure is not counted as a passing check.

A subsequent Android Kotlin compile exposed a missing `Context` parameter in the newly hardened Dynadot family-sync helper. The helper now receives the caller context explicitly and can persist per-family success state. The corrected app build, quality and emulator integration workflows have been retriggered; do not treat the preceding failed runs as acceptance passes.
