## Explicit availability labels

The following visible options now have their own pages and are deliberately labelled **SERVICE COMING SOON** rather than appearing as implemented controls:

1. **Deployments:** publishing a reviewed Workbench draft to production and Workbench-specific deployment rollback.
2. **DNS management:** automatic creation/update of public DNS records and continuous DNS TXT ownership revalidation. The current Relay Node validates its configured DNS TXT proof at startup.
3. **Cloudflare Access:** in-app creation, editing and verification of Cloudflare Access policies. Those policies must currently be configured in the Cloudflare dashboard.

Static website release rollback remains available in Websites & files → Releases; it is distinct from the not-yet-available Workbench deployment workflow.

## Layout and system-bar changes

- MainActivity now opts into edge-to-edge and applies status-bar padding to the app header.
- The main content consumes Scaffold insets, respects the IME and is vertically scrollable.
- Main content is capped at 840 dp and centered on wider displays rather than stretching full-width on tablets.
- Login, biometric unlock and site preview surfaces now account for status and navigation bars; login and biometric content scroll and react to the keyboard.
- Status/navigation bar icon appearance follows the active light/dark theme.
- Website file actions are arranged in two rows with weighted buttons to avoid a four-button horizontal overflow.
- Device enrollment OS and architecture fields are stacked on narrow screens.
- Activity event names and timestamps are separated so long labels do not push timestamps off-screen.
- Hosting, Websites, Workbench and Devices now have smaller workflow-specific page selectors.

This is a responsive single-column layout with page-level navigation, not yet a tablet-specific two-pane design.

## Required visual and functional acceptance

The updated instrumentation tests are intended to exercise the new page destinations and capture screenshots/hierarchy artifacts. They must pass on the exact candidate SHA before UI acceptance can be marked complete.

Still required on API 26, 33 and 35 emulators and named physical devices:
- Compact phone, large phone and tablet; portrait and landscape.
- 150% and 200% system font scale; TalkBack traversal, switch access, focus order and touch-target review.
- Status bar, gesture navigation, three-button navigation, camera cutouts, keyboard/IME and short-height screens.
- Loading, empty, success, offline, permission-denied, error and destructive-confirmation states for every relevant workflow.
- Real start/stop schedule checks through Doze, reboot, timezone change, clock change, force-stop, battery restrictions and delayed alarms.
- Real website import/backup/restore, Relay public visitor journey, Cloudflare Tunnel journey, device enrollment/revocation and runtime lifecycle recovery.

**Conclusion:** The app now has a much clearer page structure and explicit availability labels. This is an engineering UI pass, not release sign-off. Do not mark the UI gate PASS until the updated CI and physical-device acceptance evidence is attached to the exact release candidate.
