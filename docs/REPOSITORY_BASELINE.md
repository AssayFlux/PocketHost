## Implemented source boundaries

### Main Android app and static hosting

- Kotlin + Jetpack Compose app; Android manifest declares minSdk 26 and targetSdk 35. Gradle declares app versionName 0.1.0.
- Main app includes Home, Dashboard, Sites/file operations, Workbench, Learn, Settings and a Devices view when **Command Center + Server** mode is selected.
- Exactly two persisted mobile modes exist: `SERVER_ONLY` and `COMMAND_CENTER_SERVER`. Both retain website hosting.
- General settings include System/Light/Dark appearance, named classic palettes, optional biometric app unlock, and auto-start-on-boot setting.
- The biometric gate is optional local app protection. The main Android app does **not** currently present a conventional username/password login screen. Owner/session/passkey login exists in the separate browser console; the local management API provides pairing/approval flows.
- The app's main page is vertically scrollable. Native device settings, permissions, notification, foreground-service and battery behavior still require physical-device acceptance.
- Static website folder and ZIP import exist in `SiteImporter.kt`. The source constant is **500,000,000 bytes** for ZIP input and independently for expanded website content; file count 5,000, total archive entries 10,000 and depth 32.
- The Rust engine is a JNI library using Tokio/Hyper. It serves HTTP, binds loopback by default and can bind LAN when explicitly enabled. It implements hostname routing, static file/range/MIME handling, SPA index fallback, visitor access modes (public/private/restricted), Basic authentication and rate/connection limits.
- The Rust engine has a separate **500,000,000-byte (500 MB decimal) per-file response cap**, 16 active connections, 32 queued connections and bounded per-site admission. The Rust per-file serving cap is 500,000,000 bytes (500 MB decimal). Manual single-file import is 50 MiB; text editing is 256 KiB.
- Android local management API, pairing/approval, diagnostics, service lifecycle, telemetry, encrypted backup and recovery source exist.

### Cloudflare Tunnel

- Android integration source exists: `CloudflareTokenStore.kt`, `CloudflareTunnelRuntime.kt`, foreground-service supervision and UI for saving/removing a named tunnel token and starting/stopping the connector.
- Token storage uses AES-GCM with Android Keystore. The connector receives its token through the `TUNNEL_TOKEN` environment variable, not a command-line argument.
- `scripts/build-cloudflared-android.sh` builds the pinned upstream connector for Android ABIs. The generated executable is not checked into Git; CI generates and uploads it as an artifact.
- The app does not automatically create Cloudflare DNS records or public-hostname routes. The owner must configure the named tunnel and its public hostname/origin in Cloudflare.
- Source/build integration exists; live custom-domain DNS, TLS, HTTP redirect, visitor content and failure recovery have not been externally accepted in this snapshot.

### AssayFlux Relay

- Android `RelayAgent.kt` exists. It uses an outbound authenticated HTTPS Server-Sent Events stream and posts bounded visitor responses back to the gateway. It does not open an unsolicited public listener on the phone.
- The Relay agent obtains its endpoint and dedicated token from `RelayCredentialStore`, encrypted with Android Keystore AES-GCM. Android Network settings provide independent endpoint/credential configuration and connection controls. Node-side credential issuance remains open.
- The Relay client forwards bounded HTTP requests to the local Rust website engine. Current source limits request/response bodies to 8 MiB, allows GET/HEAD/POST/PUT/DELETE/OPTIONS, and uses bounded concurrency/queueing and a 45-second gateway wait.
- `control-plane/src/relay.rs` contains an in-memory Relay session/pending-request hub. The hub limits pending work to 32 global and 8 per device; sessions and pending requests are not durable across process restart.
- `control-plane/src/main.rs` contains the visitor gateway, DNS TXT hostname proof, route registration, and a separate visitor listener. Hostname route records are stored in PostgreSQL; the live Relay session hub is in memory.
- The same executable also contains the full admin/device control API and requires `DATABASE_URL`, PostgreSQL migrations, a long administrator token and a control API hostname at startup. It starts separate control and visitor listeners (defaults 8080 and 8081).
- `control-plane/compose.yaml` provides PostgreSQL, the Rust service, Caddy public TLS profile and an optional Cloudflare Tunnel profile. Caddy owns public ports 80/443; its current HTTP listener redirects to HTTPS. Relay visitor requests require a trusted HTTPS frontend. There is no configurable plain-HTTP content mode in the current Relay implementation.
- `web-console/src/ui/RemoteControlPlane.tsx` includes Relay hostname registration, DNS TXT challenge display, verification and deletion UI. Android Network settings now expose independent Relay endpoint/credential configuration; standalone-node hostname/TXT/TLS provisioning remains open.
- The current Alpha tree contains `relay-node/Cargo.toml`, but that directory has no `src/main.rs` or other implementation files, tests, installer or service unit. It is a Cargo manifest scaffold only, not a runnable Relay engine or Android service. The current gateway remains coupled to the fleet control-plane process/PostgreSQL and registered fleet device credentials; the Android host-side RelayCredentialStore is already independent.

### What “self-hosted Relay without a VPS” means

A paid VPS is not a product requirement. The approved v0.1.0 Relay design is a native Android service bundled in the main Pocket Host APK, with Linux-native packaging deferred to v0.1.1. However, the gateway still needs a network path that is publicly reachable by the owner's domain:

- A public IPv4 address with router port forwarding for TCP 80/443, or
- A globally routed IPv6 address with the firewall permitting the required inbound ports, plus correct DNS A/AAAA records and TLS.

If the only available network is behind carrier-grade NAT (CGNAT) and there is no globally reachable IPv6 or port-forwardable public address, DNS cannot make that phone an Internet-facing gateway. A publicly reachable owner-controlled node elsewhere is then required; Cloudflare Tunnel can remain an optional third-party fallback. This is a network constraint, not a Pocket Host limitation that software can bypass.

The **target architecture** is a lightweight native Android AssayFlux Relay service bundled in the Pocket Host APK. It does not require the full fleet control plane, a paid VPS, Docker or PostgreSQL. This target is **not implemented in the audited source snapshot**.

### Runtimes and Workbench

- `runtime-worker/` is a separate Android companion APK/application ID and UID. It currently bundles both CPython 3.11 (Chaquopy) and Node.js mobile 24.22.1 (JNI/libnode); they are not yet separate independently downloadable runtime APKs.
- Node.js SDK files are downloaded at build time from a pinned release and checked against a SHA-256 digest. The SDK/native binaries are generated build inputs, not committed files.
- Python and Node project importers, services, Binder IPC and runtime state/metrics source exist. Both runtime catalog entries remain `in-progress`; neither is a hardened hostile-code multi-tenant sandbox. Python project code runs under the companion UID; Node runs in a separate process in that companion app.
- Runtime Library has 20 JSON catalog manifests: Python and Node are `in-progress`; the remaining 18 languages are catalog-only planned placeholders with no downloadable runtime artifacts.
- Workbench source exists in `WorkbenchWorkspaceManager.kt` and `PocketHostWorkbenchScreen.kt`: private per-site draft workspace, explorer, basic text editor, save, file/folder operations, change digests and local immutable commit snapshots.
- Workbench does not yet provide isolated live preview, TypeScript compilation, validated owner-approved production publishing or full rollback workflow. Its workspace is capped at 50 MiB, with bounded file/text/commit counts.
- The separate web console is React 18.3.1, TypeScript 5.7.2 and Vite 6.0.5. It is a browser operator console, not a main-app Android runtime or the phone's website build tool.

### Device fabric and protocol

- Protocol 1.0 includes JSON schemas for device hello, enrollment challenge, job envelope and role grant, plus default-deny role/job policy manifests and Python validators/tests.
- Android device-trust source includes owner identity, challenge/proof, role-grant and revocation foundations.
- Linux agent source is a Python 3.11+ package with identity/trust verification, HTTPS polling, SQLite state/idempotency, typed allow-listed job execution and bounded storage snapshot tasks. It is a preview implementation, not production device acceptance.
- No Windows/macOS/iOS agent package or native Android Relay implementation exists in this snapshot.

### Backup and storage limits

- The current full-app backup path is `ApplicationBackupManager.kt`, not the legacy `SiteBackupManager.kt`.
- Full-app backup limits are 500,000,000 bytes static website root, 50 MiB Python project, 100 MiB Node project, 650,000,000 bytes total uncompressed and 680,000,000 bytes encrypted archive. Device-bound credentials and selected secrets are excluded.
- The static-site backup cap matches the 500,000,000-byte importer expanded-content allowance. Near-limit backup/restore, free-space preflight and physical-device recovery tests remain open.
- Other independent limits exist in Python/Node project importers, Workbench, remote deployment artifact transfer and Rust per-file serving; do not conflate them.

## UI/source discrepancies found

- The Settings > Network copy in `MainActivity.kt` says “No built-in visitor password yet” and recommends Cloudflare Access, but the Rust engine and SiteRegistry already implement private/restricted visitor credentials and Basic authentication. The copy is stale and should be corrected.
- The Network UI exposes Cloudflare controls, local hostname-to-site routing and independent AssayFlux Relay endpoint/credential setup. It does not yet provision node identities, host credentials or hostnames on the native Android Relay service.
- The app's optional biometric unlock is not a full mobile account/login page. The browser console has the separate owner/admin login and passkey flow.
